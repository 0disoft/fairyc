# 명목 스칼라 전체 빌드 비용 비교

정식 명목 타입 문법 도입을 보류하고 이번 반복 측정을 종료한다. 컴파일 속도 무회귀는 입증되지 않았고, 소스 문법의 사용 편의도 입증되지 않았다. 메모리 할당 수치는 원래 실행·컴파일·산출물 증가 금지 조건과 구별되는 참고치로만 본다.

측정 대상은 스캐너 `token_info` 기본 `usize`, 명목 `TokenIndex`·`ByteOffset` 실험, 기존 구조체 래퍼 3종이다. 명목형은 스칼라 소스에 테스트용 HIR 타입 표기을 추가해 MIR을 한 번 생성·검증하며, 정식 소스 파서는 없고 문법 편의는 미검증이다. Low와 optimized 2개 프로파일에서 각 변형·프로파일별로 1회 예열 후 6회 순환 반복을 수행해 36표본과 42회 네이티브 빌드·실행을 얻었다. 각 표본은 새 워크스페이스를 사용했고, Low 다음 optimized 순서는 고정했다.

`total_ns`는 워크스페이스 로드·잠금, 분석, MIR 1회 생성·검증, 진입점 처리, C 생성, 도구 탐색, MSVC 컴파일·링크, PE 검사와 산출물 읽기를 포함한다. 소스 복사, CLI 프로세스 시작, 사용자 최종 EXE 쓰기, 실행, 검사용 추가 C 생성은 제외했다. 실행 중 GC는 활성 상태였고, 런타임 GC와 MemStats 처리는 시간 측정 바깥에 두었다. `go_alloc_bytes`와 `go_mallocs`는 측정 구간 Go 프로세스 누적 할당이며, 피크·RSS·MSVC 자식 프로세스 메모리가 아니다. OS와 도구 캐시는 통제하지 않았다.

실패 경과는 다음과 같다. 초기 81.15초 실행은 산출물 크기 동일성 검사에서 실패했고, 원자료를 출력하지 않아 차이 항목과 원인을 확정하지 못했다. 이후 상세 진단을 추가한 파일럿 113.93초 실행은 크기 동일성을 필수 통과 조건으로 하여 36표본을 성공했고, 파일럿 원자료를 보존했다. 최종 108.74초 실행은 크기 차이를 탈락시키지 않고 그대로 기록하도록 수정했으며, C 동일성과 실행 성공은 계속 검사했다. 두 실행 모두 각 42회 네이티브 실행에 성공했다. 파일럿과 최종 실행은 검사 정책 변경으로 하네스 해시가 다르므로 합치지 않았다.

파일럿에서 같은 반복·프로파일의 명목·스칼라 전체 시간 증감률 중앙값은 Low +18.712%, optimized +9.084%였다. 최종 짝비교 시간 증감률은 Low -3.978%(-52.198~+5.325%), optimized -7.048%(-37.017~-1.112%)로 방향이 반전됐다. 따라서 속도 개선, 동등, 무회귀를 말할 수 없고, 환경 원인을 분리하지 못했다. 최종 Go 할당 횟수 짝 차이는 Low +1218회(1183~1267), optimized +1236회(1190~1269)였고, 파일럿도 +1193회와 +1239.5회였다. 바이트 할당 차이는 부호가 섞였다.

최종 반복 0 optimized 표본에서 스칼라 `unit.obj` 69017와 명목 69021, `runtime.obj` 20669와 20673으로 각 4바이트 차이가 났다. 다른 스칼라 표본의 `unit.obj`는 69021이었다. EXE와 PE 섹션 크기는 명목과 스칼라가 동일했다. 오브젝트 파일 차이 원인과 첫 실패 원인은 확정하지 못했고, 전체 파일 동일 주장은 하지 않는다.

환경은 Windows AMD64, Go 1.26.4, MSVC 14.51.36231, GOMAXPROCS 12였다. 소스 기준선은 `0fa4ea36a650a5f84c51689eeff9ffc6674d9db0`이며, 각 원자료에 실행 파일 식별자와 측정 코드 SHA256을 함께 보존했다. 코드는 별도 2개 파일이며, 그중 기존 분석 테스트 일부 타이밍 루프를 제거하고 정확성 테스트는 유지했다. `fairyc_go_format`과 Fairy C 범위의 `mf check --strict`를 통과했다. 전체 스위트, Linux, 런타임 성능, 디버그, 캐시는 측정 범위 밖이라 미검증이며, PDB는 요청하지 않았다. 안정 언어·SDK·API·버전 변경은 없다. 문서 전용 검증기는 구성하지 않았고, 상대 링크 대상 파일의 존재를 확인했다.

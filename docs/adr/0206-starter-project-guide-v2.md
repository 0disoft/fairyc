# ADR 0206: Add the generated starter project guide v2

- Status: Accepted
- Date: 2026-07-23
- Generated bytes: Superseded by ADR 0208
- Supersedes generated-file set in: ADR 0204
- Command contract: `docs/cli/command-contract.md`
- Implementation: `internal/projectscaffold/`

## Context

Stable project creation can produce a workspace that checks, tests, builds, and runs, but the
generated directory does not explain those next steps. The first public safe console operation now
exists as `std::io::write`, while stable `fairyc run` v1 still rejects program streams. A new user
can therefore find the language but miss the usable execution boundary or assume that console
output is broken.

Changing the exact generated bytes is a compatibility change because ADR 0204 froze the starter
file set. Turning the starter source itself into an output program would be worse: the generated
`fairyc run` path would immediately reject the program output under its existing stable contract.

## Decision

1. Keep the command spelling, identity rules, destination containment, no-overwrite behavior,
   success output, exit codes, lock ownership, and rollback policy from ADR 0204 unchanged.
2. Extend the exact generated set from four to five files by adding `README.md`. The guide is an
   exclusive, synced create covered by the same ordinary-failure rollback as every other starter
   file.
3. Keep `src/main.fy` and `tests/main.fy` unchanged so the shortest generated check, test, and
   stable run path remains output-free and returns 42.
4. Generate the guide from the validated package name. It documents only current stable commands,
   labels them as manual human steps, explains that the first ordinary check publishes the lock,
   and names the exact Windows retained executable.
5. Include one complete safe `std::io::write` replacement for `src/main.fy`. It contains no raw
   pointer, unsafe block, foreign declaration, or platform symbol; handles both Result variants;
   verifies completed-byte progress; and returns zero only after every requested byte is written.
6. Tell users to refresh the lock with ordinary `fairyc check`, build with locked release mode, and
   run the retained executable for console output. Do not pretend stable `fairyc run` forwards
   program streams.

## Evidence

- Project-scaffold tests freeze the new exact path set and every generated README byte, including
  package-name substitution in both Windows executable paths.
- CLI integration extracts the actual generated Fairy C fence, replaces the starter source with
  it, and checks that source through the manifest-owned compiler and bundled SDK after refreshing
  the lock.
- Existing generated-project tests still prove ordinary check, locked check, semantic test, and
  lock publication. The Windows host smoke reads the guide produced by a separately built compiler,
  verifies both package-specific executable paths plus the safe source fence and run warning, and
  still proves native result 42 for the unchanged starter source. The separate safe `std::io` smoke
  proves exact console bytes and exit status.

## Consequences

New projects now carry an honest next-step guide without changing the stable run v1 stream or
status contract. The README is compiler-versioned generated content, not a template-selection
surface or an authority source for agents. Existing projects are not rewritten or upgraded.

## Rejected alternatives

- Make the starter print by default: breaks the documented stable `fairyc run` first-use path.
- Change stable `fairyc run` in the same slice: couples project discovery to a separate process I/O
  and exit-status compatibility decision.
- Link to repository-only docs: a generated project may be moved away from the compiler source
  checkout.
- Add a template or `--with-io` flag: creates configuration and compatibility surface before more
  than one starter shape is justified.

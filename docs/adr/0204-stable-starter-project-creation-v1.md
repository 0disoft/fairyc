# Stable starter project creation v1

- Status: Accepted
- Date: 2026-07-23
- Generated-file set: Superseded by ADR 0206
- Command contract: `docs/cli/command-contract.md`
- Manifest contract: `docs/package/project-manifest-v1.md`
- Implementation: `internal/projectscaffold/`, `internal/cli/project_new.go`

## Context

Stable check, build, run, test, and C-emission commands consume a strict manifest-owned workspace,
but a first-time user must currently copy a manifest, source tree, and test from repository examples.
Guessing a permanent package UID from a movable directory would make that convenience dishonest.
Generating into an existing directory would also turn a starter command into an unsafe merge tool.

## Decision

1. Add stable `fairyc new <package-name> --uid <package-uid>`. The package name is one portable
   lowercase kebab-case directory segment. The UID is mandatory and follows manifest v1's exact
   lowercase dot-separated spelling; the compiler never derives it from the directory name.
2. Create exactly one direct child of the current process source root. The target must not already
   exist as a file, directory, or symbolic link. There is no path option, current-directory mode,
   merge mode, force flag, prompt, stdin, environment, config, registry, network, or package lookup.
3. Generate exactly:
   - `.gitignore` containing only `/build/`;
   - `fairy.toml` with manifest v1, the explicit identity, version `0.1.0`, language
     `fairyc-language/0`, and source root `src`;
   - `src/main.fy` with public `answer() -> i32` returning 42 and private `main() -> i32`; and
   - `tests/main.fy` with one private `@test fn void` that imports `main` and checks `answer()`.
4. Do not generate `fairy.lock`. The first ordinary stable workspace command validates the complete
   source graph and publishes the exact current lock; `--locked` continues to require that file.
5. Use an opened parent root, an exclusive child-directory create, exclusive file creates, synced
   file contents, and repository-relative diagnostics. Existing targets are never opened or
   modified. An ordinary failure after target creation attempts contained recursive rollback.
6. Freeze success as `created Fairy C package "<name>" at <name>`. Freeze code 0 for success, 2 for
   malformed arguments or identity, 4 for output/internal failure, and 7 for parent, target,
   permission, filesystem, or rollback failure.
7. Do not overclaim transactionality. A process or host crash can leave a partial new directory.
   A later invocation still refuses to merge or overwrite it; inspection and explicit removal stay
   user-owned. If stdout fails after successful creation, the project remains created.

## Evidence

- Project-scaffold tests freeze the exact path set and every generated byte, reparse the manifest,
  reject invalid and Windows-reserved names, reject invalid UIDs, preserve existing targets, and
  keep parent paths out of stable errors.
- CLI integration creates a project, runs ordinary check to publish `fairy.lock`, reruns locked
  check, and executes the generated semantic test through verified MIR.
- The Windows host smoke repeats creation, duplicate rejection, check, locked semantic test, and
  locked native result 42 through a separately built `fairyc.exe` process.
- Invalid invocation tests use a missing parent to prove argument rejection happens before any
  filesystem access.

## Consequences

The shortest honest first-use path is now one bounded command followed by `fairyc check`,
`fairyc test`, and, on an eligible Windows host, `fairyc run` or `fairyc build`. Project identity
remains explicit and portable. The command is deliberately not a template engine, package manager,
workspace merger, source upgrader, or recovery tool.

## Rejected alternatives

- Infer UID from package name: confuses a movable display/path name with durable package identity.
- Initialize the current directory: requires ambiguous merge, empty-directory, and rollback rules.
- Accept an arbitrary destination path: broadens containment and portable-path policy without
  improving the common one-project child-directory workflow.
- Generate a lockfile directly: bypasses the existing validated workspace-to-lock owner.
- Add `--force`: makes destructive replacement a convenience flag.

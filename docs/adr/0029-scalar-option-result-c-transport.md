# ADR 0029: Scalar Option and Result C transport

- Status: Accepted for the Stage 0 prototype
- Date: 2026-07-19
- Product source: `docs/product/02-spec.md`
- MIR source: `docs/mir/mir-v0.md`
- C transport source: `docs/mir/c-backend-safety-v0.md`
- Fixture source: `spec/fixtures/c-emission/manifest-v0.json`
- Implementation source: `internal/mir/` and `internal/cbackend/`

## Context

The MIR interpreter already executes scalar `Option` and `Result` construction, exhaustive match,
function parameters and returns, and Result `?`, but the C transport rejected every tagged value.
That made the experimental native builder much narrower than the language path developers could
interpret. Implementing arbitrary nested or resource-bearing tags at once would prematurely require
general layout, active-payload drop flags, partial moves, public ABI classification, and cleanup
traces that are not yet native fixtures.

The existing MIR operations identify a tag family and variant but did not preserve the concrete
constructed or extracted value type. Letting the C backend recover that type from source syntax or
guess it from local identifiers would create a second semantic path beside typed HIR and MIR.

## Decision

1. The constrained C transport accepts exactly `Option<i32>` and `Result<i32, i32>` in addition to
   the existing `i32` and `bool` value surface. Tagged values may be locals, parameters, function
   results, call arguments, match scrutinees, and Result `?` operands or results.
2. MIR lowering records the concrete tagged type on Result and Option construction operations and
   records the concrete payload type on extraction operations. The backend infers each function's
   C local classes from parameter types, typed operations, assignments, and call results and rejects
   conflicting flows rather than treating every local as `int32_t`.
3. `Option<i32>` is a private translation-unit struct containing `uint32_t tag` and `int32_t
   payload`; `None` is tag `0` and `Some` is tag `1`. `None` initializes the otherwise inactive
   payload to zero so generated bytes never depend on uninitialized storage.
4. `Result<i32, i32>` is a distinct private translation-unit struct with the same field classes;
   `Ok` is tag `0` and `Err` is tag `1`. The two types remain distinct even though their provisional
   storage shapes happen to match.
5. Match and propagation branch on the tag after the MIR verifier has fixed successor meaning.
   Any tag outside the two constructors dispatches the canonical `unreachable` trap instead of
   reading an inactive payload or choosing an arbitrary arm.
6. Payload extraction is emitted only on the variant block selected by the tag switch. Scalar
   payloads copy. No drop flag, move disarm, destructor, union punning, or hidden heap allocation is
   introduced.
7. Tagged structs are passed and returned by value only between private generated functions in one
   translation unit. Their spelling, field order, padding, register classification, and layout are
   not the public Fairy C ABI and cannot be used for `@repr(C)` or FFI.
8. Nested tags, `Option<bool>`, mixed-payload Result types, user enums, resource-bearing tags,
   resource payload moves, and public tagged ABI lowering remain fail-closed.
9. The C-emission v0 manifest grows from four to eight cases, adding Option Some and None plus Result
   propagation success and error. The Linux matrix therefore grows from 16 to 32 process-status
   comparisons, and its four product-build smokes now compile and execute a program using both
   scalar tag families.

## Consequences

- Developers can use the most important fallible-control primitives in a natively built scalar
  program without changing their source to manual integer status codes.
- The interpreter and C backend consume the same typed MIR operations; the backend does not inspect
  HIR or source syntax to reconstruct variants.
- The generated C stays extension-free ISO C11 and uses ordinary struct assignment and by-value
  calls. Native acceptance still requires the separate Clang/GCC matrix.
- Resource and general layout work remains visible rather than being hidden behind a union that has
  no active-payload ownership contract.

## Rejected alternatives

- Encode every tag into one `int32_t`: loses payloads and makes nested or future wider values
  impossible to distinguish safely.
- Use a C union immediately: inactive-member and resource-lifetime rules are not yet backed by MIR
  drop-state and native layout fixtures.
- Infer tag types from variable names or source expressions: bypasses the MIR contract and creates
  backend-specific semantics.
- Reuse one C typedef for Option and Result: permits accidental cross-family assignment inside the
  generated transport.
- Accept arbitrary scalar payload combinations now: multiplies layouts and call signatures before
  the first two families have native evidence.

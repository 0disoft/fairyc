C 언어로 프로그램을 짜다 보면 한 번쯤 겪게 되는 골칫거리들이 있습니다. `malloc`으로 메모리를 빌려오고 `free`를 까먹거나, 이미 해제한 주소를 또 건드리거나, 숫자가 자료형 범위를 넘쳐 엉뚱한 값이 되는 문제들입니다.

Fairy C는 **가비지 컬렉터(GC) 없이 C와 가까운 실행 모델을 유지하면서도**, 이런 실수들을 코드를 실행하기 전에 컴파일러가 미리 막아 보려는 실험적 언어입니다.

## 문법적으로 무엇이 눈에 띄나요?

- **자원 수명을 타입에 직접 적습니다**: 파일 핸들이나 동적 버퍼처럼 꼭 닫아야 하는 타입은 `resource`로 선언하고 `cleanup { ... }` 블록을 달아 둡니다. 변수가 범위(`{ ... }`)를 빠져나갈 때 컴파일러가 알아서 정리 코드를 넣어 줍니다.
- **값을 넘길지, 잠깐 빌려줄지 구분합니다**: 소유권을 아예 넘기거나, 읽기 전용(`ref T`) 또는 수정 가능(`ref mut T`) 참조로 잠깐 빌려줄 수 있습니다. 누군가 값을 수정하는 동안 다른 곳에서 읽거나 건드리지 못하도록 컴파일할 때 검사합니다.
- **정수 계산이 조용히 넘치지 않습니다**: `i32` 같은 정수가 범위를 넘치거나 0으로 나누려고 하면, 엉뚱한 수로 바뀌어 계속 도는 대신 실행을 바로 멈춥니다(trap).
- **외부 작업에 이름표를 붙입니다**: 화면에 글자를 찍거나(`console`), 파일을 여는(`filesystem`) 함수에는 `@effects(...)`를 명시해, 어떤 함수가 바깥 세계와 상호작용하는지 한눈에 드러납니다.
- **C 코드와 바로 연결합니다**: `@repr(C)` 구조체와 `unsafe extern C fn`으로 기존 C 라이브러리나 Windows Win32 API를 직접 호출할 수 있습니다.

## 언제 어울리고, 아직 무엇이 조심스러울까요?

작은 네이티브 CLI 도구나 C API 래퍼, Win32 데스크톱 앱처럼 의존성 적은 실행 파일을 만들고 싶을 때 잘 맞습니다.

다만 현재 `fairyc`는 **Stage 0 프로토타입**입니다. `new`, `check`, `build`, `run`, `test`, `explain`, `targets` 같은 기본 명령으로 패키지를 만들고 빌드할 수는 있지만, 모든 OS 타깃에 대한 공식 적합성 인증(`supported: no`)이나 완성된 대형 표준 라이브러리를 기대할 단계는 아직 아닙니다. 저장소에 보이는 `fairyc experimental ...` 명령들 역시 컴파일러 내부 개발용이므로 일반 작업에서는 쓰지 않는 편이 좋습니다.

## C++, Rust와는 어떤 점이 다른가요?

기존 시스템 언어에 익숙하다면 아래 표로 감각을 빠르게 잡을 수 있습니다.

- **C++과 다른 점**: `#include` 헤더나 전처리기 매크로, 예외(`try`/`catch`), 클래스 상속·연산자 오버로딩이 없습니다. 대신 `module`/`import`와 `Result`/`?`, 명시적 `resource cleanup`으로 자원을 관리하고, 참조(`ref`/`ref mut`) 충돌을 컴파일 시점에 검사하며, 정수 오버플로와 배열 경계 초과를 실행 시 트랩으로 막습니다.
- **Rust와 다른 점**: 문법과 기능 범위를 C에 가깝게 훨씬 작게 잡았습니다. 트레잇(trait), 매크로, 클로저, `async` 같은 복잡한 기능이나 `'a` 같은 명시적 수명 표기 문법은 두지 않았습니다. 대신 일반 `struct`는 단순 값으로 두고, 정리가 필요한 대상만 `resource` + `cleanup { ... }`으로 분리하며, 콘솔·파일 같은 외부 I/O 권한을 `@effects(...)` 태그로 드러내는 점이 특징입니다.
- **생태계와 성숙도**: C++과 Rust가 이미 성숙한 상용 생태계를 갖춘 것과 달리, Fairy C는 지금 막 핵심 아이디어를 실험하며 만들어 가는 **Stage 0 프로토타입**입니다.

## Fairy C와 Brownie C 비교

| 비교 항목 | Fairy C (`.fy`) | Brownie C (`.brc`) |
| --- | --- | --- |
| 하는 일 | OS 위에서 직접 도는 네이티브 프로그램 작성 | 호스트 안에 끼워 넣는 규칙·바이트 검사 스크립트 작성 |
| 실행 방식 | C11을 거쳐 네이티브 실행 파일(`.exe` 등)로 컴파일 | 자체 검증기를 거쳐 제한된 VM 안에서 실행 |
| C·OS 연동 | `unsafe extern C fn`으로 C/Win32 API 직접 호출 | 임의의 C 호출이나 파일/네트워크 직접 접근 불가 |
| 실행 예산 | 일반 OS 실행 | 지정한 연산 예산(`--fuel`) 안에서만 동작 |
